# MY TRAVEL MAP — PROJECT CONTEXT

## 1. Project purpose

This project is a personal travel-history web application called My Travel Map.

The application is intended primarily to run locally on a Mac laptop. It provides a detailed global map where the user records countries, cities, towns, mountains, landmarks, waypoints, and other places they have visited.

The application should remain simple to operate, require no paid mapping subscription, and keep the user's travel database under the user's control.

The current application version is

My Travel Map v7

The latest package is

`My_Travel_Map_OpenFreeMap_v7_BetterSelection_Profile_Mac.zip`

---

# 2. Core design principles

The following requirements should be preserved in all future versions.

### Local-first

The application runs locally on the user's Mac.

It is launched using

`Launch My Travel Map.command`

This starts a lightweight Python local web server.

The application is then accessed through a local browser address such as

`127.0.0.1port`

The application should NOT require deployment to a public server.

### User owns the data

The master travel database is

`travel-data.json`

This file normally resides in the same folder as the application.

The application must not rely on browser localStorage as its primary database.

Browser localStorage is only a fallbackmigration mechanism.

### Automatic persistence

Whenever the user

- adds a place
- edits a place
- deletes a place
- edits their profile
- merges imported travel data
- replaces imported travel data

the application must automatically update `travel-data.json`.

The user should NOT have to manually press a Save button after ordinary changes.

The app waits for confirmation from the local server that the JSON file was successfully written.

If saving fails, the UI must not pretend the change was safely committed.

### Upgrade compatibility

Future versions should continue to read older `travel-data.json` files whenever reasonably possible.

When providing a new ZIPversion, the user should keep their existing populated

`travel-data.json`

and replaceupdate the application files around it.

Do not overwrite the user's populated JSON with an empty sample during upgrades.

# 5. Launcherserver behavior

The user should launch the application using

`Launch My Travel Map.command`

rather than opening the HTML using `file`.

This is important because direct HTML execution cannot reliably write `travel-data.json`.

## Historical launcher problem

Earlier versions always attempted to use

`127.0.0.18765`

If an older Travel Map server was still running on that port, launching a newer application could accidentally open the older application.

This caused a confusing situation where

- opening the new HTML directly showed new features;
- launching through the command file showed an older version with features missing.

## Current solution

The v6+ launcherserver architecture

1. tries port 8765;
2. if occupied, automatically selects another free local port;
3. opens the browser using the actual port assigned to the new server;
4. serves HTMLJS with no-cache headers;
5. displays the application version in the UI;
6. displays the exact folderaddress in Terminal.

Future versions MUST preserve this behavior.

Never assume port 8765 is available.

# 11. Better map feature selection — v7

Earlier versions relied heavily on reverse geocoding.

This produced several problems.

For example

- clicking the text label of a city could return a district or administrative region instead of the city;
- clicking a mountain often failed to select the mountain;
- landmarks and waypoints were not reliably identified;
- the coordinates could represent the exact mouse position rather than the geographic feature.

v7 changed this.

## Current intended selection algorithm

When the user clicks the map, first use

`map.queryRenderedFeatures()`

around a small screen-space area surrounding the click.

The application evaluates the rendered vector features and ranks them.

High priority

1. mountains  peaks;
2. cities;
3. towns;
4. villages;
5. named POIs;
6. landmarks;
7. viewpoints  attractions  similar waypoints.

Low priority

- administrative boundaries;
- broad administrative regions;
- roads;
- highways;
- landcover;
- generic polygons.

If a useful named vector feature is found, use that feature's name.

For point features, use the feature's actual geographic coordinates rather than merely the location where the user clicked on the label.

Reverse geocoding is then used mainly for

- determining the country;
- filling missing information;
- fallback when no useful rendered feature exists.

Future work should continue improving this feature-selection behavior.

Accuracy when clicking labels is more important than blindly trusting reverse geocoding.

# 22. Browser localStorage

Browser localStorage exists only as a secondary mechanism.

It is NOT browser history, but clearing browsersite data can remove it.

Therefore it must not be treated as permanent travel storage.

Historical localStorage key for places

`myTravelMap.places.v2`

Profile may also have a local fallback key.

## Migration behavior

If

- `travel-data.json` is empty;
- browser localStorage contains existing places;

the application should automatically migrate the browser places into `travel-data.json`.

If both contain data and differ

DO NOT silently overwrite either database.

Instead provide

Sync browser → JSON

This lets the user deliberately copy the browser version into the master JSON file.

The UI should display a status such as

`✓ JSON connected — 87 places loaded`

This reassures the user that the real JSON file is being used.

---

# 23. Automatic save reliability

Automatic save is a critical requirement.

Every mutation should

1. update the in-memory data;
2. send the updated data to the local Python API;
3. wait for successful confirmation;
4. only then treat the operation as committed.

If the write fails

- show a clear error;
- do not silently pretend that the JSON database was updated;
- roll back the visible change when appropriate.

This applies to

- Add;
- Edit;
- Delete;
- Profile changes;
- imports.

# 25. Import behavior

Import was originally dangerous because selecting a JSON file immediately replaced the existing database.

This was changed.

Current import should present three choices

### Merge with existing

This should be the safedefault approach.

It

- keeps existing places;
- adds imported places;
- skips obvious duplicates.

Duplicate detection currently uses a combination roughly equivalent to

- normalized place name;
- normalized country;
- rounded coordinates.

Future versions may improve duplicate detection.

### Replace All

This intentionally replaces the current travel database.

Before replacement

1. clearly warn the user;
2. automatically download a backup of the current database;
3. require confirmation;
4. only then overwrite `travel-data.json`.

### Cancel

Makes no changes.

Never revert to immediate destructive replacement on import.

---

# 26. Profile handling during import

Current intended behavior

### Merge

Preserve the existing profile.

If the existing profile is empty and the imported file contains a profile, the application may adopt the imported profile.

### Replace All

If the imported file contains a profile, that profile may replace the current profile.

The pre-replacement backup must contain the old profile.

# 42. v8 update (27 Sep 2026) — CURRENT BASELINE

Current version: My Travel Map v8. Package: `My_Travel_Map_v8.zip` (folder `My_Travel_Map_v8/`).
v8 is a reliability + selection-accuracy release built from v7 against this document. All v7 behaviour retained.

Package changes
- Package does NOT ship travel-data.json (server creates it on first save) — upgrades can no longer overwrite user data.
- MapLibre GL JS 5.24.0 bundled in ./lib (no unpkg). Upgrade deliberately, not by CDN drift.
- Windows launcher added: "Launch My Travel Map (Windows).bat" (Mac .command remains primary).

Server (server.py)
- GET /api/data returns X-Data-Revision (sha1 of file). POST must send baseRevision; mismatch → 409 "stale" (protects against an old tab overwriting newer data).
- Never overwrites a travel-data.json it cannot parse (409, UI shows error).
- Preserves ALL existing top-level fields and extra profile fields; validates place coordinates.
- fsync + atomic replace; write lock; path-traversal guard; /api/info endpoint; --no-browser flag.

Frontend
- All mutations go through one commit() path: apply → POST → confirm → mirror to localStorage ONLY after success; rollback + clear error otherwise.
- Selection: country/state/province/continent place labels excluded; candidates ranked by type score minus 6 pts/px distance from click (12 px radius); "What did you mean?" chooser when distinct good candidates are within 290 pts of the best; "None of these" → clicked spot + reverse geocode. Add dialog shows what was selected.
- Map clicks on markers/popups/controls, or clicks that close a popup, no longer open Add.
- Popups built with DOM (no inline onclick). Nominatim throttled to 1 req/s with timeout.
- Filter hides markers too; "My places" fits filtered set; Collapse all/Expand all; notes preview in list; map style remembered; country grouping case-insensitive (most common spelling shown).
- Merge duplicate = same id, or same normalised name (+ same/blank country) within 1 km. Sync browser→JSON downloads a backup first.

Tests run before release: 14 server checks + 41 end-to-end browser checks (Playwright, stubbed tiles/Nominatim) — all passed. Not yet verified on real OpenFreeMap tiles or with the user's populated travel-data.json.

Decisions (user-chosen): Supabase (auth + Postgres) + Netlify static hosting; Google sign-in only; open sign-up (anyone with the link).

Package: `online/` = `site/` (drag onto Netlify Drop), `supabase-setup.sql`, `SETUP-GUIDE.txt`.
